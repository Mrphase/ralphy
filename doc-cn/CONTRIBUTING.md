# 贡献指南 (Contributing to Ralphy)

## 代码更改理念

### 保持更改小而专注

- **一次提交一个逻辑更改** - 每次提交应该只做一件事
- 如果任务感觉太大，请将其分解为子任务
- 多个小提交优于一个大提交
- 在每次更改后运行反馈循环，而不是在最后运行

**质量胜于速度。小步快跑积少成多。**

### 任务优先级

在处理任务时，请按此顺序安排优先级：

1. **架构决策和核心抽象** - 首先构建正确的坚实基础
2. **模块之间的集成点** - 确保各个组件正确连接
3. **未知的未知和探索性工作** - 尽早通过探索性工作降低风险
4. **标准特性和实现** - 建立在坚实基础之上
5. **打磨、清理和快速获胜** - 把容易完成的任务留到后面

**在有风险的工作上快速试错。把容易获胜的任务留到最后。**

## 代码质量标准

### 编写简洁的代码

编写任何代码后，问问自己：

> "高级工程师会说这过于复杂吗？"

如果是，请**简化**。

### 避免过度工程

- 只进行直接要求或明显必要的更改
- 不要添加未被要求的功能、重构代码或进行超出要求的“改进”
- 修复错误不需要清理周围的代码
- 一个简单的功能不需要额外的可配置性
- 不要向未更改的代码添加注释或类型注释
- 仅在逻辑不言自明的地方添加注释

### 整洁的代码实践

- 不仅仅为了凑数而填充文件
- **不要留下死代码** - 如果未使用，请将其完全删除
- 没有为了向后兼容而重命名未使用的 `_vars` 等黑客行为
- 不要为删除的代码重新导出类型
- 没有为删除的代码保留 `// removed` 的注释
- 保持条理、简洁、干净

## 开发设置

```bash
# 克隆仓库
git clone https://github.com/michaelshimeles/ralphy.git
cd ralphy/cli

# 安装依赖
bun install

# 运行代码检查
bun run check

# 运行测试
bun test

# 构建
bun run build
```

## 技术栈

- **运行时**: Bun（Node.js 18+ 后备）
- **语言**: TypeScript (strict mode)
- **代码检查/格式化**: Biome
- **CLI 框架**: Commander

## 代码风格

代码风格由 Biome 强制执行。在提交之前运行 `bun run check`。

- **缩进**: 制表符 (Tabs)
- **行宽**: 100 个字符
- **行尾**: LF
- **导入**: Biome 自动整理

## 提交准则

1. 一次提交包含一个逻辑更改
2. 写描述性的提交信息
3. 格式: `type: 简短描述`

**格式类型:**
- `feat:` 新功能
- `fix:` 错误修复
- `refactor:` 代码重组（无行为改变）
- `docs:` 文档
- `test:` 测试添加/更改
- `chore:` 维护任务

## Pull Request 流程

1. 从 `main` 创建一个功能分支
2. 按照上述准则进行更改
3. 确保所有测试通过: `bun test`
4. 确保代码检查通过: `bun run check`
5. 提交包含明确更改描述的 PR
